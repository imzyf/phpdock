# PHPDOCK

## Introduction

My PHP development environment for Docker, built on
[Laradock](https://laradock.io/) with prebuilt php-fpm/php-worker/workspace
images and local customizations layered on top (see "How customization
works" below).

## Quick Start

```bash
make up       # core containers: php-fpm, nginx, postgres, redis
make up-all   # all containers
make down
make build
make generate # regenerate docker-compose.yml from upstream + */compose.override.yml
make config   # print the fully merged compose config
docker-compose exec workspace bash
```

`make up`/`make up-all` create `.env` from `.env.example` on first run.
Edit `.env` to override anything — your `.env` always wins over each
service's `defaults.env`.

## How customization works

Docker Compose does the merging natively (requires Compose v2.24+ for
the `!override` tag). One small script wires it up.

Each service directory holds upstream's files and ours side by side:

```
php-fpm/
  compose.yml            # upstream — refreshed by `make sync`, don't edit
  defaults.env           # upstream — refreshed by `make sync`, don't edit
  compose.override.yml   # ours — layered on top of compose.yml
  Dockerfile             # ours — one-line FROM on a prebuilt image
```

| File | Who owns it |
|---|---|
| `<service>/compose.yml`, `<service>/defaults.env` | upstream, refreshed by `make sync` — don't edit |
| `<service>/compose.override.yml` | **you** — layered on top of the upstream compose |
| `php-fpm/Dockerfile`, `php-worker/Dockerfile`, `workspace/Dockerfile` | **you** — one-line `FROM` on a prebuilt image |
| `.env.example` | **you** — hand-written, shared settings + overrides |
| `docker-compose.yml` | generated by `make generate` — don't edit |

`bin/generate-docker-compose.sh` takes upstream's root
`docker-compose.yml` (~150 services) and

1. prunes `include` and `volumes` down to `SYNC_DIRS`, and
2. for every `<service>/compose.override.yml` that exists, rewrites that
   service's `path` into a *list*:

```yaml
include:
  - path:
      - php-fpm/compose.yml            # upstream base
      - php-fpm/compose.override.yml   # our customization
    project_directory: .
    env_file: php-fpm/defaults.env
```

Compose merges the later file onto the earlier one. Maps merge
recursively, so anything the override doesn't mention (`volumes`,
`expose`, `environment`, `depends_on`, …) is kept. The `!override` tag
replaces a whole node instead of merging it — that's how
`php-fpm/compose.override.yml` drops upstream's ~90 build args and keeps
only the handful the prebuilt image needs. (`!reset` deletes a node.)

**To customize a service:** drop a `compose.override.yml` into its
directory and run `make generate` — the include list is wired up for
you. Check the result with `make config`. To see everything we've
customized: `ls */compose.override.yml`.

Override files need no entry in `EXCLUDE_GLOBS`: `make sync` only walks
the files upstream actually has, so a name upstream doesn't use is never
touched.

Keeping generation for the root file means the *structure* (which
services exist, how upstream wires `env_file` / `project_directory`)
tracks upstream automatically, while the override files own the
*content*.

## Syncing from upstream

```bash
make sync         # uses a 1-day clone cache
make sync-force   # ignore the cache
```

This refreshes the upstream-owned files listed in `bin/.sync-config.sh`
(`SYNC_DIRS`), mirrors a few reference-only files (upstream's `.env.example`
lands at the root as `.env.upstream`, its root `docker-compose.yml` under
`bin/.upstream/`), then runs `make generate`. After syncing, `git diff` shows
exactly what upstream changed so you can decide what to carry over — including
new keys in `.env.upstream` that may be worth adding to ours.

`.env.upstream` is not just a reference copy: `make generate` wires it into
every `include` entry's `env_file` as a fallback, so the compose files we keep
can reference variables owned by services we do not run (for example
`${VARNISH_BACKEND_PORT}` in `nginx/compose.yml`) without `docker compose
config` warning about them. It is used for interpolation only — nothing is
injected into a container. Precedence is shell env > root `.env` > `env_file`
list, so whatever you put in `.env` always wins.

Files we hand-maintain under an upstream name (the three Dockerfiles,
pruned `.ini` files) are listed in `EXCLUDE_GLOBS` so the sync never
clobbers them.
